# Code Audit — 2026-07-21

**Scope:** ACP / Aegis repo. Backend/core code only (per operator direction — docs and UI not audited).
**Method:** Round 1 (CI + surface metrics) + Round 2 (ground-level review of auth, audit chain, decision/policy, money path — 4 parallel agents, each claim verified) + Round 3 (raw SQL, SSRF/outbound, unsafe deserialization, shell primitives, CORS, Dockerfile, untouched services) + Round 4 (security primitives: randomness, weak hashes, JWT algorithm enforcement, verify_exp/verify_aud, non-constant-time comparisons, alembic destructiveness, prompt-injection regex, API key entropy) + Round 5 (gateway middleware stack + registry service deep-read) + Round 6 (behavior, forensics, insight, learning, identity_graph, flight_recorder, api ARE engine, autonomy playbooks — 3 parallel agents, every claim verified against the exact code). Any claim I could not verify is under **Contradicted claims** or **Open questions**, not under findings.
**Verdict:** The green-CI-is-a-lie problem is real. Underneath it, the code has *fewer* live bugs than the CI honesty gap suggests — and at the *primitive* level this platform is at top-1% shape: all randomness through `secrets`, JWT alg confusion blocked at every decode site, non-constant-time secret comparisons absent, weak-hash sites correctly `usedforsecurity=False`, prompt-injection patterns free of ReDoS shapes, destructive alembic downgrade guarded by a `RuntimeError`, secret comparisons via `compare_digest`, granted permissions treated as a positive allow-list (fake grants inert). **The real gaps live at *composition seams*** — where two components trust each other in a way that lets a mistake in one silently create an opening in the other. Ranked-by-blast-radius composition gaps found across all 6 rounds: (a) pending audit-log trigger will break the billing-status closure loop on apply (P0-5), (b) per-employee LLM budget check is a TOCTOU race (P1-6), (c) 32 fail-open `except Exception: pass` sites including one at the auth boundary (P0-4/P1-8), (d) SSRF defense is real but half-wired — two implementations, two attacker-controllable URL sinks stored without validation (P1-9/P1-10), (e) Clerk JWT decode skips `verify_aud` (P2-8), (f) registry silently suppresses cache-invalidation failures + no role check (P1-11/P1-12), (g) gateway middleware order contradicts its own comment (P2-9), (h) API service `/internal/throttle` lacks the mesh auth every sibling uses (P1-13), (i) learning repository queries drop `tenant_id` entirely — works only because a column happens to be globally unique (P1-14), (j) behavior `/check` silently None-scopes on bad UUID and falls back to a tenant-less Redis key (P1-15), (k) insight SCAN fallback is not tenant-scoped (P1-16). Fix the composition seams first; the primitives are already there.

### P1-11  Registry silently swallows cache invalidation failures on every permission change
- **Where:** `services/registry/service.py:135, 150, 180`
- **Evidence** (representative — same pattern at all 3 sites):
  ```python
  try:
      permission = await self.perm_repo.create(tenant_id, agent_id, payload)
      with contextlib.suppress(Exception):
          await _invalidate_agent_caches(agent_id)
      return PermissionResponse.model_validate(permission)
  ```
- **Meaning:** `_invalidate_agent_caches` deletes the `acp:agent:meta:{agent_id}` key AND sets the `acp:agent:perms_dirty:{agent_id}` tombstone. If Redis is unreachable, both operations fail; the DB row is written; the gateway keeps serving the STALE cached permission set until its independent TTL expires (memory notes 60s cache staleness window). During that window, a revoked permission is still granted; a newly granted permission is still absent. There is no log line and no metric — the change appears to succeed.
- **Fix cost:** Small. Do not fail the request — but surface the failure so operators can catch a Redis blip before customer-visible policy drift.

### P1-17  ARE destructive-action authorization has no matching rego rule
- **Where:** `services/api/are_executor.py:229` combined with the rego bundle at `services/policy/policies/*.rego`
- **Evidence:**

### P1-12  Registry endpoints have no role-based authorization; defense-in-depth on permission grant/revoke depends entirely on the gateway
- **Where:** `services/registry/router.py:520-619` (permission POST/GET/DELETE) and `service.py:138-179` (`add_permission`, `remove_permission`).
- **Evidence:** Each write endpoint takes `tenant_id: Annotated[uuid.UUID, Depends(get_tenant_id)]` and immediately writes. No role check anywhere in the handler or service layer. Grep across `services/registry/` for `require_role|OWNER|require_admin|require_owner|has_permission_role`: empty.
- **Meaning:** The registry's model is that the gateway has already enforced the caller's role. That is a defensible design when every call goes through the gateway's mesh, but the registry is exposed on the internal network and speaks the mesh JWT — a compromised sibling service, a mesh-JWT leak, or a future admin API that talks directly to the registry gets to grant any tool permission to any agent in any tenant that shares the mesh secret. There is no second wall.
- **Fix cost:** Small–medium. Add an explicit role check in the service layer that trusts a `caller_role` field from the mesh JWT: `if caller_role not in {"OWNER", "ADMIN"}: raise HTTPException(403)`. Same for `remove_permission` and `update_agent`. Belt and braces.

### P2-9  Gateway middleware order contradicts its own comment; duplicate 401 rate-limit path
- **Where:** `services/gateway/main.py:528-566`
- **Evidence:** Line 528-529 comment on the inline `_rate_limit_401` middleware reads: *"Sits OUTERMOST so it sees the final response after auth resolved."* The registration order is:
  1. line 515 — inline `@app.middleware("http")` `_v1_prefix_alias`
  2. line 533 — inline `@app.middleware("http")` `_rate_limit_401`
  3. line 560 — `app.add_middleware(SecurityMiddleware, redis=redis)`
  4. line 566 — `app.add_middleware(SecurityHeadersMiddleware)`

  In Starlette, later-added middleware sits OUTERMOST — so on request, the actual order is `SecurityHeadersMiddleware → SecurityMiddleware → _rate_limit_401 → _v1_prefix_alias → route`. `_rate_limit_401` is NOT outermost.
- **Meaning:** `SecurityMiddleware` (`services/gateway/middleware.py:518`) emits 401 directly at line 646 for missing/invalid bearers WITHOUT calling `call_next()` — so its 401s never reach the outer `_rate_limit_401`. `SecurityMiddleware` has its own burst-on-401 counter (line 2434+), which is what actually gates enumeration. Result: two 401-rate-limiters with overlapping-but-different behavior, and the outer one silently misses the majority of 401s it was written to handle.
- **Impact:** Not a security bypass — SecurityMiddleware's counter is the real gate — but confusing enough that a future maintainer will delete the wrong one.
- **Fix cost:** XS. Either delete `_rate_limit_401` (redundant), or move `SecurityMiddleware`+`SecurityHeadersMiddleware` registrations BEFORE the inline decorator so `_rate_limit_401` really is outermost, and fix the comment either way.

### P2-13  Identity-graph blast-radius BFS is bounded but expensive
- **Where:** `services/identity_graph/repository.py:145-166`
- **Evidence:**
  ```python
  for _ in range(max(1, min(depth, 6))):
      if not frontier:
          break
      stmt = select(GraphEdge).where(
          GraphEdge.tenant_id == tenant_id,
          GraphEdge.src_node_id.in_(list(frontier)),
  ```

### P2-14  ARE pending-approval Redis key includes a caller-controlled `request_id`
- **Where:** `services/api/are_worker.py:305-316`
- **Evidence:**
  ```python
  async def _store_pending_approval(...):
      approval_key = f"{rule_id}:{incident.get('request_id', uuid.uuid4().hex)}"
      key = f"acp:{tenant_id}:are:pending:{approval_key}"
  ```

- **Meaning:** Cross-tenant hijack is blocked by the `{tenant_id}` prefix. - **Fix cost:** Small. Server-side generate the approval key with `secrets.token_urlsafe(16)` regardless of the incoming `request_id` and return it to the approver flow; store the `request_id` inside the value, not in the key.

### P2-12  Registry agent-quarantine may not persist to DB
- **Where:** `services/registry/router.py:435-479`

### P2-8  Clerk JWT validation skips `verify_aud`
- **Where:** `sdk/common/clerk_auth.py:232-238`
- **Evidence:**
  ```python
  payload = jwt.decode(
      token,
      jwk,
      algorithms=[jwk.get("alg") or "RS256"],
      issuer=self._issuer,
      options={"verify_aud": False, "require_iat": False},
  )
  ```
- **Meaning:** Issuer IS checked (`issuer=self._issuer`), so the token has to come from the correct Clerk instance. But if a Clerk organization runs multiple audience-scoped applications (typical: separate `staging` / `prod` frontends off one Clerk root), a token minted for one audience can be replayed against another — the audience is the field the JWT spec designates for that separation. Skipping `verify_aud` is a standard defense-in-depth downgrade.
- **Not a bypass**: any Clerk-signed token from the org will be accepted regardless of aud. Impact scales with how many aegis-adjacent audiences the same Clerk org signs for.
- **Fix cost:** Trivial. Pass `audience=settings.CLERK_AUDIENCE` (or the configured value) and set `verify_aud: True`. Ship a config with a canonical `aegis` audience.

### P2-7  `X-Internal-Secret` is in CORS `allow_headers`
- **Where:** `sdk/utils.py:509-511` — every service that uses the shared FastAPI setup allows:
  ```python
  allow_headers=["Content-Type", "Authorization", "X-Request-ID",
                 "X-Tenant-ID", "X-Agent-ID", "X-ACP-Tool", "X-Timestamp",
                 "X-Internal-Secret", "X-API-Key"],
  ```
  with `allow_credentials=True`.
- **Meaning:** `X-Internal-Secret` is the service-to-service mesh secret. A browser has no legitimate reason to send it. Server-to-server calls do not go through the browser's CORS check, so removing it costs nothing.
- **Fix cost:** Trivial. Delete `"X-Internal-Secret"` from the `allow_headers` tuple.
